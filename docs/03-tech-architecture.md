## 2. Ключевое архитектурное решение

**Симуляция отделена от рендера.**

```
src/
  sim/          Чистая TS-логика БЕЗ импорта Phaser. Детерминирована (seed RNG), фиксированный шаг 1/60.
  render/       Phaser-сцены: читают состояние sim и рисуют. Ввод превращается в Command для sim.
  data/         Данные: враги, оружие, улучшения, биомы, мета-узлы (TS с типами или JSON).
  meta/         Сохранения, Эхо-хранилище, мета-дерево (чистая логика + localStorage адаптер).
  ui/           HUD, меню, выбор улучшений (DOM или Phaser GameObjects).
  audio/        Обёртка над ZzFX и музыкой.
  tools/        Ботовый симулятор баланса (запуск в Node).
tests/          unit/ и e2e/
public/         Статика: спрайты, звук, шрифты
docs/           Эти документы
```

### Зачем так
1. **Ботовый баланс:** `node tools/balance.ts` прогоняет 1000 забегов за секунды без браузера. Это сильный аргумент в критериях «Game Design» и «AI Usage».
2. **Тесты без браузера:** урон, синергии, Эхо-снимок проверяются юнит-тестами.
3. **Меньше багов от AI:** логика в маленьких чистых модулях, которые модель может целиком держать в контексте.
4. **Детерминизм:** сид забега позволяет воспроизвести баг и делиться «сидом дня».

### Ядро sim
- `World`: массивы сущностей (SoA или простые объекты), `step(dt, input)`.
- `Entity`: `id, kind, x, y, vx, vy, hp, radius, team, statuses`.
- Пространственная хеш-сетка для коллизий (ячейка 64 px).
- `StatBlock`: единственная точка расчёта характеристик (база + модификаторы от улучшений и меты).
- `Effect/Trigger`-система для синергий: улучшение подписывается на события (`onHit, onKill, onStatusApplied, onDash`) и возвращает действия. Синергия реализуется как условие по тегам.
- `RNG`: mulberry32 с сидом. **Запрещено `Math.random()` в sim.**
- `Events`: очередь событий для рендера (взрыв, смерть, пикап), чтобы эффекты и звук не были связаны с логикой.

### Рендер
- Один `GameScene` для боя, `HubScene`, `MenuScene`, `BootScene`.
- Спрайты врагов берутся из пула (`Phaser.GameObjects.Group` с `maxSize`).
- Для 150 врагов и сотен снарядов: атласы текстур, без постобработки, `pixelArt: true`.
- Камера следует за игроком, арена фиксированного размера (например 1600x1200).

## 3. Производительность и качество (критерий Technical Quality)

| Метрика | Цель | Как проверяем |
|---|---|---|
| Размер билда | < 5 МБ (gzip) | `vite build`, размер `dist` |
| Загрузка до меню | < 3 с на 4G | Lighthouse / DevTools Throttling |
| FPS | 60 при 150 врагах, минимум 45 на слабом ноутбуке | Режим `?debug=1` показывает FPS и число сущностей |
| Крашей | 0 за 5 прогонов по 15 минут | Playwright soak-тест с ботом |
| Сохранения | Переживают перезагрузку, повреждённые данные не ломают игру | Юнит-тесты с мусорным `localStorage` |

### Меры
- Версия схемы сохранения (`schemaVersion`) и миграции.
- `try/catch` вокруг чтения сохранений с откатом к дефолту.
- `visibilitychange`: пауза при уходе со вкладки.
- Масштабирование `Phaser.Scale.FIT` с центрированием.
- Любые внешние ресурсы (шрифты, CDN) — **только локальные**, чтобы игра не зависела от интернета и сторонних сервисов.

## 4. Тесты

### Юнит (Vitest)
- Формула урона и `StatBlock`.
- Генерация волн: `generateWave(biome, room, seed)` стабильна.
- Выбор улучшений: нет дубликатов, учитывается редкость и `luck`.
- Эхо: снимок -> загрузка -> сила.
- Мета: покупка узла, нехватка валюты, миграция схемы.

### Баланс-бот
- Простая политика: двигаться от ближайших врагов к центру, подбирать пикапы, выбирать улучшение по приоритетам тега.
- Выход: CSV и таблица в консоли (процент побед, средняя глубина, среднее время, по билдам).
- Запуск после каждого изменения чисел.

### E2E (Playwright)
- `smoke.spec.ts`: открыть страницу, дойти до меню, начать забег, прожить 30 с, убедиться в отсутствии ошибок в консоли.
- `soak.spec.ts`: бот в браузере с ускорением (`?speed=4&bot=1`), 10 минут.
- `save.spec.ts`: смерть -> Эхо появилось -> перезагрузка -> Эхо на месте.

## 5. Деплой

1. `npm.cmd run build` -> `dist/`.
2. GitHub Pages: публичный репозиторий `echo`, в настройках Pages выбрать источник «GitHub Actions», workflow собирает `dist` и публикует (`actions/upload-pages-artifact` + `actions/deploy-pages`). Игроку регистрация **не нужна**. В `vite.config.ts` обязателен `base: './'`.
3. Резерв: загрузить `dist` как HTML5 на itch.io (нужна пометка «играть в браузере», игра публичная).
4. Проверить финальную ссылку: приватное окно, другой браузер (Chrome, Firefox, Safari по возможности), телефон.
5. В анкете указать **один** основной URL. Резерв положить в ванпейджер.

## 6. Риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| Просадка FPS при множестве сущностей | Средняя | Пулы, хеш-сетка, лимиты, профиль на ранней стадии (этап 1) |
| Баги синергий | Высокая | Данные плюс триггеры, юнит-тест на каждую синергию |
| Аудио не стартует (политика автоплея) | Высокая | Старт звука только после первого клика («Нажмите, чтобы начать») |
| Потеря сохранений | Низкая | Версионирование, резервная копия в `localStorage` под вторым ключом |
| AI генерирует несовместимый код (Phaser 4 вместо 3) | Средняя | В `AGENTS.md` зафиксировать версию и запрет обновления |
| Лицензии на ассеты | Средняя | Только CC0 и свои; файл `docs/CREDITS.md` |

## 7. Работа с DeepSeek Harness (DeepSeek 4.1)

Практические правила, чтобы модель не теряла контекст и не ломала проект:

1. **Один чат = одна задача из `STATE.md`.** После завершения: обновить `STATE.md`, сделать коммит, начать новый чат с `RESUME-PROMPT.md`.
2. **Маленькие шаги.** Не просить «сделай всю боевую систему». Просить «реализуй `StatBlock` и тесты к нему».
3. **Тест перед следующим шагом.** После каждой задачи запуск `npm.cmd run test`, `npm.cmd run build`. Только зелёное идёт дальше.
4. **Коммиты часто:** `git commit` после каждой зелёной задачи. Откат дешевле исправления.
5. **Не позволять модели переписывать архитектуру** без запроса. В `AGENTS.md` это зафиксировано.
6. **Проверять результат своими глазами:** запустить игру и сыграть минуту. Тесты не видят, весело ли.
7. **Вести `docs/06-ai-log.md` по ходу работы**, а не в конце. Это прямой материал для анкеты.
8. Использовать `subagent` для независимых задач (например, написание данных врагов отдельно от кода), но по одной зоне файлов, чтобы не было конфликтов.
9. Если что-то в среде не работает (`npm`, права), смотреть раздел про Windows выше, а не придумывать обходные пути.
